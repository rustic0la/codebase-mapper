# Что взять из Self-Testing AI Agents

Заметки к [PLAN.md](./PLAN.md), по материалам [воркшопа Steve Kinney](https://stevekinney.com/courses/self-testing-ai-agents). Проверено 6 октября 2026 года. Это дополнение к процессу разработки карты кодовой базы, без изменения выбранного стека.

## Что именно даёт курс

Курс учит снабжать агента, который пишет код, автоматическими проверками и материалами для исправления ошибок. Учебное приложение — SvelteKit, но автор отдельно объясняет перенос процесса на React/Next.js. Его подход применим и к нашему локальному MVP. Он не заменяет проверки правдивости AI-объяснений внутри будущего продукта: это отдельная задача этапов 5–6 плана.

## Дополнительные главы для интерфейса

Следующее — адаптация материалов курса к нашей карте:

- [Deterministic State and Test Isolation](https://stevekinney.com/courses/self-testing-ai-agents/deterministic-state-and-test-isolation): запускать UI-проверки на фиксированном JSON графа; фиксировать commit приложения, viewport и выбранный файл.
- [Visual Regression](https://stevekinney.com/courses/self-testing-ai-agents/visual-regression-as-a-feedback-loop): сохранить три состояния — раскрытая папка, выбранный файл и область влияния. Эталонные снимки обновлять при намеренном изменении интерфейса с объяснением причины.
- [Performance Budgets](https://stevekinney.com/courses/self-testing-ai-agents/performance-budgets-as-a-feedback-loop): измерять размер bundle, время раскладки и взаимодействие с большой картой. Выбрать собственные бюджеты по исходным измерениям.
- [Playwright Test Agents](https://stevekinney.com/courses/self-testing-ai-agents/playwright-test-agents): planner и generator помогают подготовить сценарии; healer требует контроля. По [официальной документации](https://playwright.dev/docs/test-agents) его результат может быть passing или skipped при сломанной функциональности. Для нас skipped означает невыполненную приёмку. Команды настройки сверять с текущей официальной документацией; копирование команд курса без проверки может дать устаревший вариант.

## Минимальный процесс для первых этапов

1. **До реализации:** записать сценарий и ожидаемые результаты. Для парсера вручную создать маленький эталон связей; для UI определить действия пользователя.
2. **После изменения:** агент запускает проверку типов, релевантные Vitest-тесты и сборку. При изменении карты выполняет Playwright-сценарий раскрытия папки, выбора файла и перехода к зависимости.
3. **При сбое:** сохраняет пакет воспроизведения в `artifacts/<run-id>/`, читает его, исправляет причину, повторяет упавшую проверку, затем остальные проверки задачи. Это предлагаемый путь, команды ещё предстоит создать.
4. **Перед сдачей:** перечисляет результаты и изменения проверок. Отдельный проход ревью ищет противоречия спецификации и риски. CI проверяет актуальную ветку в чистом окружении.
5. **Приёмка:** человек повторяет ключевой сценарий и оценивает ограничения. Автоматический успех не расширяет обещание продукта: граф импортов остаётся графом импортов.

## Пробная задача для проверки процесса

Добавить literal `require` в парсер. Эталон содержит обычный require, вычисляемый путь, отсутствующий файл и смешанный файл с ESM. Агент должен показать новый разрешённый тип связи, причины неразрешённых конструкций и сохранение ранее ожидаемых ESM-рёбер.

Наш дополнительный эксперимент: внести контролируемую ошибку в реализации на временной ветке и убедиться, что нужный тест падает, пакет сбоя создаётся, а агент способен воспроизвести и исправить причину. Удалять или ослаблять ожидаемое поведение для получения зелёного статуса нельзя.

## Что отложить

Custom MCP для проверок, AI-triage в JSON, nightly и много браузеров добавлять при конкретной потребности. Для старта важнее корректный эталон парсера, один браузерный сценарий и доступные материалы сбоя. Проверки поведения модели, метрики выдуманных путей и LangSmith остаются отдельной частью плана.
