# Что взять из Self-Testing AI Agents

Заметки к [PLAN.md](./PLAN.md), по материалам [воркшопа Steve Kinney](https://stevekinney.com/courses/self-testing-ai-agents). Проверено 6 октября 2026 года. После уточнения пользователя продукт — CLI для GitHub Actions с генерируемым отчётом. Упоминания UI ниже относятся к будущему HTML-репортеру; отдельное веб-приложение не требуется.

## Что именно даёт курс

Курс учит снабжать агента, который пишет код, автоматическими проверками и материалами для исправления ошибок. Учебное приложение — SvelteKit, но автор отдельно объясняет перенос процесса на React/Next.js. Его подход применим и к нашему CLI: команда воспроизведения, ожидаемые/фактические файлы и exit code. Он не заменяет проверки правдивости AI-объяснений внутри будущего продукта: это отдельная задача будущих расширений.

## Дополнительные главы для интерфейса

Следующее — адаптация материалов курса к нашей карте:

- [Deterministic State and Test Isolation](https://stevekinney.com/courses/self-testing-ai-agents/deterministic-state-and-test-isolation): запускать UI-проверки на фиксированном JSON графа; фиксировать commit приложения, viewport и выбранный файл.
- [Visual Regression](https://stevekinney.com/courses/self-testing-ai-agents/visual-regression-as-a-feedback-loop): сохранить три состояния — раскрытая папка, выбранный файл и область влияния. Эталонные снимки обновлять при намеренном изменении интерфейса с объяснением причины.
- [Performance Budgets](https://stevekinney.com/courses/self-testing-ai-agents/performance-budgets-as-a-feedback-loop): измерять размер bundle, время раскладки и взаимодействие с большой картой. Выбрать собственные бюджеты по исходным измерениям.
- [Playwright Test Agents](https://stevekinney.com/courses/self-testing-ai-agents/playwright-test-agents): planner и generator помогают подготовить сценарии; healer требует контроля. По [официальной документации](https://playwright.dev/docs/test-agents) его результат может быть passing или skipped при сломанной функциональности. Для нас skipped означает невыполненную приёмку. Команды настройки сверять с текущей официальной документацией; копирование команд курса без проверки может дать устаревший вариант.

## Минимальный процесс для первых этапов

1. **До реализации:** записать сценарий и ожидаемые результаты. Для парсера вручную создать маленький эталон связей; для UI определить действия пользователя.
2. **После изменения:** агент запускает проверку типов, релевантные Vitest-тесты и сборку. При изменении карты выполняет Playwright-сценарий раскрытия папки, выбора файла и перехода к зависимости.
3. **При сбое:** сохраняет пакет воспроизведения в `artifacts/<run-id>/`, читает его, исправляет причину, повторяет упавшую проверку, затем остальные проверки задачи. Это предлагаемый путь, команды ещё предстоит создать.
4. **Перед сдачей:** перечисляет результаты и изменения проверок. Отдельный проход ревью ищет противоречия спецификации и риски. CI проверяет актуальную ветку в чистом окружении.
5. **Приёмка:** человек повторяет ключевой сценарий и оценивает ограничения. Автоматический успех не расширяет обещание продукта: граф импортов остаётся графом импортов.

## Пробная задача для проверки процесса

Добавить literal `require` в парсер. Эталон содержит обычный require, вычисляемый путь, отсутствующий файл и смешанный файл с ESM. Агент должен показать новый разрешённый тип связи, причины неразрешённых конструкций и сохранение ранее ожидаемых ESM-рёбер.

Наш дополнительный эксперимент: внести контролируемую ошибку в реализации на временной ветке и убедиться, что нужный тест падает, пакет сбоя создаётся, а агент способен воспроизвести и исправить причину. Удалять или ослаблять ожидаемое поведение для получения зелёного статуса нельзя.

## Что отложить

Custom MCP для проверок, AI-triage в JSON, nightly и много браузеров добавлять при конкретной потребности. Для старта важнее корректный эталон парсера, один браузерный сценарий и доступные материалы сбоя. Проверки поведения модели, метрики выдуманных путей и LangSmith остаются отдельной частью плана.

## Протокол proof of work для продукта

Это наше расширение процесса: материалы проверок становятся данными интерфейса ревью. Оно не приписывается курсу. Начать с Markdown-отчётов, затем определить JSON-схему и пакет с относительными путями к вложенным артефактам. Пакет должен переноситься между локальным запуском и демо без абсолютных путей машины автора.

| Часть пакета    | Что сохраняем                                                                                                            | Что показывает интерфейс                                 |
| --------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| Формат и задача | Версия схемы, ID задачи, описание, критерии приёмки со стабильными ID                                                    | Какой результат ожидался                                 |
| Снимки          | Базовый и итоговый снимок, commit SHA при наличии, хеш манифеста файлов                                                  | К какой версии относятся изменения и результаты          |
| Изменения       | Добавленные, удалённые, изменённые файлы и явные переименования, снимки исходников                                       | Что агент изменил; ссылка в граф и внешний diff          |
| Проверки        | ID проверки и критериев, команда и cwd относительно проекта, время начала/окончания, exit code, результат, происхождение | Что выполнялось, как завершилось и кто сообщил результат |
| Артефакты       | Логи, expected/actual JSON и diff, скриншоты, Playwright trace; пути, типы и хеши файлов                                 | Материалы, которые можно открыть или скачать             |
| Ограничения     | Незапущенные проверки, причины пропуска, непокрытые критерии, оставшиеся замечания                                       | Что требует дополнительной проверки                      |

Хеш снимка вычислять по отсортированному манифесту путей и содержимого файлов в явно определённой области задачи; включать новые и изменённые незакоммиченные файлы. В неё входят исходники, конфигурация, lockfile, проверяемая спецификация и проверки, от которых зависит результат. Commit SHA без состояния рабочего дерева недостаточно. Область и исключения сохранять вместе с манифестом. Хеши подтверждают согласованность материалов, но не честность их автора.

В интерфейсе держать раздельно три признака: **результат проверки**, **происхождение**, **актуальность для снимка**. Например, «успешно / заявлено агентом / другой снимок» и «успешно / повторено человеком / этот снимок» имеют разный смысл. Отсутствие проверки не обозначать успехом; skipped не выполняет приёмку. CI-запуск должен ссылаться на конкретный запуск и анализируемый снимок; просто поле `source: ci` в загруженном JSON остаётся заявлением автора пакета.

Импорт валидирует схему, наличие и хеши вложений, сопоставление со снимком и разрешённые относительные пути внутри пакета. Это проверка целостности пакета. Независимое подтверждение выполнения появляется после повторного запуска конкретной проверки на том же снимке или проверки записи из доверенного источника; проверка содержательности самой приёмки остаётся отдельной задачей.

Сначала определить пакет и CLI-репортер. Потом добавить адаптеры результатов уже выполненных проверок нашего проекта и CI, включая неуспешные результаты. Не выполнять команды из импортированного отчёта и скрипты анализируемого репозитория. Существующий явно настроенный pipeline передаёт результаты генератору отчёта. GitHub Actions входит в основной план после локального запуска; файловый контракт позволяет использовать одну команду в обоих местах.

**Приёмка протокола:** показать настоящий пакет выполненной задачи; связать критерий с логом и соответствующим изменённым файлом; распознать чужой снимок, отсутствующий артефакт и повреждённый пакет. Успешно загруженный отчёт агента не становится автоматически подтверждённым результатом.
